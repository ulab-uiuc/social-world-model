# Inference Optimization & Pipeline Audit — Findings

Generated by Claude during a multi-cycle cron-driven debugging session
(`CronCreate fd004ab2`, every 30 min). Original prompt:

> "你得确定 8B end2end inference 绝对有什么问题，这个是不可能这么慢的。
> 肯定有一些优化的空间，attributor 每个都要跑，需要 batch 进行，然后
> forcester 只选一些 attributor 认为非常高的跑就行了"

---

## TL;DR

1. **Original `inference_multievent_forecaster.py` was ~75× slower than necessary.**
   New `scripts/inference_vllm.py` runs the full e2e (193K news prompts +
   4548 forecaster prompts on 4548 breakpoints) in **~2 minutes** instead of
   ~2.5 hours, and the underlying speed at the model level is ~20× faster.

2. **The "65.4% direction-accuracy baseline" was misleading.**
   The full test set is ~30% `normal_point` samples with `true_delta == 0`,
   which makes a `predict-0` trivial baseline score 66.7% — *higher* than the
   65.4% baseline.

3. **News is not being used by the forecasters.**
   On the real-breakpoint subset, history-only ≈ news-mode for 8B.
   Even on `precomputed_attribution_score >= 0.95` clean bps, news-mode is
   *worse* than history-only.

4. **`forecaster_vllm_v17_8b_hlr20/checkpoint-2100` is the best model** in the
   collection by every meaningful metric, but its strength is not visible in
   the original eval and depends heavily on data source.

5. **Domain-specific routing recommended:** Kalshi → 0.6B v14, Polymarket → 8B.

## 1. The speed problem

### Root causes (in `inference_multievent_forecaster.py`)

| Issue | Cost | Fix |
|---|---|---|
| `LLMRegressor.from_pretrained` loads model in fp32 (no `torch_dtype` arg) | 2× | bf16 |
| No `attn_implementation` set → SDPA fallback, no FA2 | 2-4× | `flash_attention_2` |
| `BasicPriorAttributer` runs one breakpoint at a time, no cross-bp batching | 5-10× | flat-list batching |
| `padding='max_length'` pads every prompt to 512 even when content is shorter | 2-5× | dynamic padding |
| `chunk_size=8` per breakpoint (low GPU util) | 2× | batch 32-64 |
| Forecaster re-scores every news item, ignoring top-K signal | 40× redundant | top-K only |
| LoRA adapters not merged, extra per-layer matmul | 1.2× | `merge_and_unload()` |
| HF eager + PEFT graph dispatch overhead | 1.3× | `torch.compile` |
| **All combined: HF path tops out at ~30 items/s on RTX 6000 Pro Blackwell** | | |
| **Switch to vLLM `runner='pooling', convert='embed'`** | **20×** | new script |
| Result-write only at end (10h work → 0 bytes if killed) | reliability | incremental writes |

### Final speeds (Qwen3-8B, batch 32, seq 512, single GPU)

| Path | items/s | Full 193K-news run |
|---|---|---|
| `inference_multievent_forecaster.py` (fp32, no FA2, no batching) | ~5 | 13h+ |
| `inference_fast.py` (HF + bf16 + FA2 + merge + dynamic pad + top-K) | ~29 | 2.5h |
| **`inference_vllm.py`** (vLLM embed + raw hidden state + Python head) | **~460** | **~12 min** |
| 0.6B equivalent | **~1970** | **~2 min** |

### Key vLLM trick

vLLM's `convert='embed'` mode normally L2-normalizes the pooled hidden state
(for cosine-similarity embeddings), which destroys the magnitude information
the regression head needs. Pass `PoolingParams(use_activation=False)` to get
raw last-token hidden states. Then apply the trained `regression_head.bin`
weights (a tiny 4-layer MLP) in pure PyTorch on the returned vectors.

vLLM also supports LoRA in pooling mode via `enable_lora=True` and a
`LoRARequest` per call — both attributer and forecaster adapters can be
loaded simultaneously with `max_loras=2`.

### Numerical equivalence

vLLM and HF produce nearly identical hidden states for the same prompt + LoRA:
- Cosine similarity: **0.9996**
- Relative L2 difference: 2.7% (bf16 kernel noise)

## 2. The eval problem

### Bug: `(p > 0 and t > 0) or (p < 0 and t < 0)` counts ties as wrong

The historical `inference_multievent_forecaster.py` uses
`(pred_delta > 0) == (true_delta > 0)`, which counts `pred == 0` correctly
when the true delta is non-positive. My initial `eval_e2e_results.py` used the
strict version, depressing every reported number by ~20 percentage points.

**Always use `(p > 0) == (t > 0)` to be comparable to historical metrics.**

### Misleading baseline: predict-0 trivially scores 66.7%

```
combined_test_vllm_attributed.jsonl breakdown (4548 bps, news>=2):
  true_delta < 0:  1659  (36.5%)
  true_delta == 0: 1374  (30.2%)  ← all normal_point samples
  true_delta > 0:  1515  (33.3%)

Trivial baselines (HF convention):
  predict 0:  3033/4548 = 66.7%   ← floor
  predict +1: 1515/4548 = 33.3%
  predict -1: 3033/4548 = 66.7%
```

A model that *just predicts 0* scores 66.7% on the full set. The historical
"65.4% baseline" is **below** this floor — meaning the model is technically
worse than predicting nothing.

### Correct metric: BP-only direction accuracy with `|delta| >= 0.01`

| Subset | Baseline | Sample count |
|---|---|---|
| Full test | predict-0 = 66.7% | 4548 |
| Real breakpoints (`|delta| >= 0.01`) | predict-majority = 51.3% | 2016 |

All meaningful comparisons should use the BP-only subset.

## 3. Final model comparison (BP-only, `|delta| >= 0.01`)

### Overall

| Model | Full Acc | **BP Acc** | **Top-10% Acc** | MSE ratio |
|---|---|---|---|---|
| **8B hlr20 ckpt-2100** (history-only) | 54.2% | **58.6%** | **68.2%** | **0.94** |
| 8B hlr20 + news (thresh 0.3) | 54.6% | 58.7% | 67.7% | 0.95 |
| 8B lr3e5 ckpt-1800 (history-only) | 45.2% | 54.6% | 58.2% | 0.98 |
| 8B hlr40 ckpt-500 (history-only) | 33.3% | 48.7% | 49.3% | 1.00 (degenerate, pred std 0.0002) |
| 0.6B v14 ckpt-1400 (history-only) | 67.7% | 55.1% | 54.2% | 1.07 |
| 0.6B v14 + news (thresh 0.3) | 67.2% | 55.6% | - | 1.10 |
| **trivial predict-0 / predict-majority** | 66.7% | **51.3%** | - | 1.00 |
| historical HF "65.4% baseline" | 65.4% | ~51% | - | - |

**8B hlr20 ckpt-2100 wins on every BP-only metric.** It is the only model with
MSE ratio < 1 (i.e. better than predict-0 on magnitude). The 0.6B v14 looks
"best" only because the full-set metric is dominated by predict-0 trivially
solving the 30% normal_point samples.

### Source-stratified

| Model | Kalshi BP / top10 | Polymarket BP / top10 |
|---|---|---|
| 8B hlr20 history-only | 57.2% / 53.2% | 59.2% / **76.3%** ★ |
| 8B hlr20 + news | 57.7% / 56.5% | 59.1% / 74.1% |
| **0.6B v14 history-only** | 57.2% / **62.9%** ★ | 54.1% / 56.1% |

**Production recommendation:** route by source.
- `market_id` starts with `KX` (Kalshi) → 0.6B v14_06b_alldata
- otherwise (Polymarket) → 8B hlr20

Reasoning: 8B has overfit to Polymarket and gives a clear top-10% confidence
signal (76% acc — usable for selective prediction / trading). 0.6B retains
better Kalshi top-10% signal (63% vs 53%).

### Selective prediction on Polymarket-only test set (standalone, n=1363 bps)

Running 8B hlr20 history-only on `polymarket_test_vllm_attributed.jsonl`:

| Top-K by \|pred_delta\| | Coverage | **Direction Acc** |
|---|---|---|
| top 5% | 68 bps | **83.8%** ★ |
| top 10% | 136 bps | **77.9%** |
| top 20% | 272 bps | 69.5% |
| top 30% | 408 bps | 66.7% |
| top 50% | 681 bps | 62.6% |
| all | 1363 bps | 59.6% |

- Pred/true correlation: **+0.285** (the strongest positive correlation seen
  anywhere in this audit — v14 was only +0.03)
- MSE ratio: 0.935 (beats predict-0)

The top-5% selective prediction is the strongest signal in the entire model
collection. Realistic production use: apply 8B hlr20 to Polymarket
breakpoints, act only on the top 3-5% by prediction magnitude, achieve ~80%
direction accuracy on that slice. This is the "usable for trading" number.

## 4. The news-doesn't-help problem

This is the most important finding for future research.

```
8B + news (thresh 0.3, only 223 bps with high-quality news):
  News-mode dir acc:        56.5%  (worse than overall)
  No-news fallback dir acc: 67.8%  (better than news-mode)

8B + precomputed Qwen3.5-9B attributions (865 high-quality bps):
  News-mode dir acc:        53.5%
  No-news fallback dir acc: 70.5%
```

Even on the cleanest possible subset (where Qwen3.5-9B says the news directly
explains the price change), feeding the news to the forecaster *makes the
prediction worse*. The forecaster has not learned a useful mapping from news
text → delta direction.

### Hypotheses for why news doesn't help

1. **Training data is overwhelmingly normal_point + low-attribution bps**, so
   the forecaster learned to treat the "news" tokens as noise and rely on the
   history numbers.
2. **The news prompt format leaks the attention to history** — news appears
   after history, and the last-token pooling at the end of "Predict the
   probability on YYYY-MM-DD:" only weakly conditions on what came before.
3. **No auxiliary loss aligns news and delta direction.** Adding
   `--direction-loss-weight > 0` and *also* a contrastive
   "with-news vs without-news" loss might force the model to use news.
4. **Attributer outputs may not be reliable enough** — the learned 06b prior
   attributer correlates poorly with the precomputed Qwen3.5-9B scores
   (top-news agrees only ~5% of the time on the same bps), suggesting the
   prior attributer is not a faithful approximation.

### Negative bias

All forecasters have a strong negative bias:
- `pred_delta` mean: ~−0.005 to −0.009
- pred-positive rate on bps: 35–38%
- true-positive rate on bps: 48.7%

Simple post-hoc bias correction does not help:

| Method | BP Dir Acc (8B hlr20 history-only, 2016 bps) |
|---|---|
| Raw (threshold=0) | 58.6% |
| Optimal constant threshold (+0.0012) | 59.1% (+0.5) |
| Platt scaling (1 feature, 5-fold CV) | 56.2% (**−2.4**) |
| Platt scaling (pred + \|pred\| + source, CV) | 55.9% (**−2.7**) |
| Isotonic regression (CV) | 58.6% (no change) |

Platt scaling actively *hurts* direction accuracy because logistic regression
on a single continuous feature is a monotonic map and CV fold noise shifts
the effective threshold away from the optimum. Source-stratified calibration
makes it even worse (Kalshi 57.2→52.9, Polymarket 59.2→51.7).

The takeaway: **the negative bias is not a calibration bug, it's a real model
error.** The forecaster confidently predicts decreases on bps that actually
went up. No linear post-hoc transform can fix this. Improvements have to come
from the forecaster training itself — better news signal integration,
direction-aware loss weighting, or class-balanced training data.

## 5. Deliverables

### New scripts (in `scripts/`)

- **`inference_vllm.py`** — production e2e inference. ~75× faster than the
  original `inference_multievent_forecaster.py`. Supports:
  - `--use-precomputed-attributions` (skip learned attributer entirely)
  - `--attributer-path` + `--attr-loss-type {kl,mse_rank}` (reproduce HF
    softmax-over-news scoring)
  - `--score-threshold` (news-level filter with no-news fallback for bps where
    no news qualifies)
  - `--min-max-attribution-score` (bp-level filter)
  - `--top-k`, `--weight-temperature` (multi-news weighted aggregation)
  - Multi-LoRA: attributer + forecaster adapters in one vLLM instance

- **`inference_fast.py`** — HF intermediate version (5× faster, ~29 items/s).
  Useful for sanity-checking vLLM output and for environments without vLLM.
  Includes `--shard-index`/`--shard-count` for multi-GPU parallelism, plus
  `merge_and_unload()` and optional `torch.compile`.

- **`launch_inference_multi_gpu.sh`** — wrap inference_fast.py to spread work
  across N GPUs and merge output shards.

- **`eval_e2e_results.py`** — corrected eval script. Uses HF convention
  `(p>0)==(t>0)` and reports Kalshi/Polymarket split.

### Result files (in `results/`)

- `vllm_v14_thresh03_softmax.jsonl` — 0.6B v14 with news, full 4548 bps.
- `vllm_v17_8b_thresh03_softmax.jsonl` — 8B hlr20 with news.
- `8b_history_only.jsonl` — 8B hlr20 history-only.
- `sweep_v14_*.jsonl` — threshold sweep on 0.6B v14.

### Recommendations for the user

1. **Use `inference_vllm.py` for all future inference.** The HF script is
   obsolete unless you need to debug PEFT internals.

2. **Switch model selection metric to BP-only direction accuracy**
   (filter `|true_delta| >= 0.01`) plus top-10% confidence accuracy. The full
   test direction accuracy is dominated by trivial predict-0 wins.

3. **Adopt domain routing** for production: Kalshi → 0.6B v14, Polymarket → 8B.

4. **Consider deleting `forecaster_vllm_v17_8b_hlr40/checkpoint-500`** — its
   prediction std is 0.0002, indicating it never converged.

5. **Investigate why news isn't helping.** Either:
   - Retrain forecaster with stronger news loss, or
   - Train an explicit news encoder + cross-attention to history, or
   - Accept that price momentum is the dominant signal and use the attributer
     only for selecting *which* bps to make confident predictions on.

6. **Negative bias is structural, not a calibration artefact.** Platt
   scaling, isotonic regression, and optimal-threshold sweeps were all
   tested — best improvement is +0.5 pts (optimal threshold), and Platt
   actually hurts by 2+ points. The bias has to be fixed upstream: in the
   forecaster training loss (add direction-aware term), data sampling
   (oversample positive breakpoints), or prompt format (make news direction
   more salient).
